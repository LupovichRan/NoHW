# חיבור Nohomework ל־Supabase

הקוד כולל חיבור אמיתי, אך הפרויקט טרם הוגדר והסכמה לא הורצה מול שרת חי. בלי הגדרה האתר נשאר בדמו מקומי.

1. צרו פרויקט Supabase חדש. ב־SQL Editor הריצו את supabase-schema.sql ואחריו subscriptions.sql, כל אחד פעם אחת. הסכמה החדשה אינה מיגרציה של הסכמה הישנה; בפרויקט שכבר מכיל school_* צריך לתכנן מיגרציה לפני הרצה.
2. ב־Authentication → URL Configuration הגדירו את כתובת האתר ב־Netlify כ־Site URL ואת כתובות החזרה המותרות. הפעילו אימות אימייל והגדירו ספק אימייל אם נדרש.
3. ב־Settings → API העתיקו Project URL ואת Publishable Key או anon הציבורי.
4. ערכו את cloud-config.js והכניסו את שני הערכים הציבוריים. לא service_role ולא secret.
5. העלו את תוכן dist לאתר ב־Netlify. ודאו שגם cloud-config.js ו־supabase.js עלו.
6. הירשמו באתר ואשרו אימייל. משתמש חדש מקבל פרופיל תלמיד.
7. מנהל הפרויקט מגדיר מורים והורים ב־SQL Editor, למשל: UPDATE public.school_profiles SET role='teacher' WHERE id='UUID_OF_TEACHER'; החליפו ב־UUID מתוך Authentication → Users. להורה השתמשו ב־role='parent'.
8. המורה נכנס ויוצר כיתה. להוספת תלמיד/מורה, הזינו את UUID של חשבון שכבר נרשם. במסך משתמשים אפשר למצוא אותו. שיוך מורה דורש פרופיל teacher; תלמיד דורש student.
9. מנהל מקשר הורה לילד: INSERT INTO public.school_guardians(parent_id,student_id) VALUES('PARENT_UUID','STUDENT_UUID');
10. בדקו עם מורה ושני תלמידים בשתי כיתות. משימה צריכה להופיע לכל תלמידי הכיתה; סימון הכנה לא ישנה מצב של ילד אחר. שאלה פרטית לא תופיע לתלמיד אחר או להורה שאינו השואל. פרסום לכיתה יחשוף רק את נוסח השאלה שהמורה אישר.

התפקיד מגיע מהשרת, ומתגי הדמו מוסתרים כשיש חיבור. הרשאות מסד RLS מגבילות קריאה וכתיבה. טיוטות AI נפרדות מהתוכן המפורסם; תשובות מתפרסמות בפעולת SQL אטומית.

האתר מתרענן מהשרת כל 30 שניות כשאין עריכה פעילה. התראות בדפדפן דורשות אתר פתוח. שיעורים ותזכורות שבועיות משותפים; אין עדיין Push כשהאתר סגור.

התמונות וההקלטות נשמרות כרגע בתוך תוכן JSON במסד, לא ב־Storage. מומלץ להתחיל בקבצים קטנים; הפרדה ל־Storage תידרש לשימוש בהיקף גדול.

בדיקות: תחביר JS ובדיקות חיבור עם Supabase מדומה. אימות חשבונות, הרצת SQL ו־RLS מול פרויקט אמיתי טרם בוצעו.

מסלול מסחרי: 3 חודשי ניסיון, לאחר מכן 9.90 ₪ לחודש למשפחה עד 4 ילדים. מורים בחינם.
הניסיון מתחיל בקישור ההורה לילד הראשון. הוספת אחים אינה מאפסת אותו. מגבלת ארבעה ילדים נאכפת בטריגר מסד עם נעילה למניעת עקיפה בבקשות מקבילות.
המחיר ומצב המנוי נשמרים במסד ואינם ניתנים לשינוי מהדפדפן. חיוב, ביטול מנוי וחסימת גישה לאחר הניסיון עדיין אינם מופעלים: שירות התשלומים לא מחובר.

בתי ספר:
כל כיתה משויכת לבית ספר. בפרויקט חדש הריצו את הסכמה הראשית העדכנית ואחריה subscriptions.sql.
אם כבר הותקנה הסכמה הישנה, הריצו רק migration-add-schools.sql לצורך שדרוג זה; הוא שומר את מזהי הכיתות ואת הנתונים.
המיגרציה מקבצת כיתות לפי המורה שיצר אותן תחת בית ספר זמני. מנהל צריך לעדכן שמות ולחבר כיתות של מורים שונים לאותו בית ספר כשהדבר מתאים.
המורה יכול ליצור בית ספר, לבחור אותו ואז להוסיף אליו כיתות. בתי ספר מוצגים למשתמש רק אם הוא יצר אותם או שיש לו גישה לכיתה בתוכם.
מורה יכול להיות משויך לכיתות בבתי ספר שונים. שתי כיתות בשם ד׳2 בבתי ספר שונים מקבלות מזהים נפרדים.
בדיקות הסינון בממשק עברו; SQL והרשאות Supabase עדיין לא הורצו מול פרויקט חי כאן.

מסכי אדמין ומנהל בית ספר:
אחרי הסכמה הראשית, subscriptions.sql ומיגרציית בתי הספר כשנדרשת, הריצו admin-invitations.sql פעם אחת.
המנהל הראשון חייב להירשם ולאמת אימייל. בעל הפרויקט מגדיר אותו כאדמין דרך SQL Editor: UPDATE public.school_profiles SET role='admin' WHERE id='UUID_OF_ADMIN';
האדמין מקים בתי ספר ומזמין מנהלי בתי ספר. המנהל יכול לערוך רק בתי ספר שהוא משויך אליהם, ליצור כיתות ולהזמין מורים והורים.
מורה מוזמן ללא כיתה מצטרף לצוות בית הספר; אחרי קבלת ההזמנה אפשר לבחור אותו כמורה אחראי ביצירת כיתה.
בהזמנת הורה יש לבחור את הילד. אחרי קבלת ההזמנה הקישור הורה–ילד נוצר ומפעיל ניסיון משפחתי בהתאם למסלול.
ההזמנות תקפות שבעה ימים, מוגבלות לאימייל המאומת של המוזמן וניתנות לביטול לפני קבלה. קבלת הזמנה ושיוך המשתמש מתבצעים בתוך פעולה אטומית במסד.
האתר מספק קישור להעתקה או פותח הודעת mailto אצל המזמין. אינו שולח הזמנות בעצמו; שליחה אוטומטית תדרוש ספק דיוור ופונקציית שרת.
לתזרים אימות האימייל הגדירו את כתובת האתר ב־Supabase URL Configuration. ההזמנה נשמרת זמנית בדפדפן; אם מאשרים אימייל במכשיר אחר, פתחו שוב את הקישור המקורי באותו מכשיר לאחר הכניסה.
הסכמה וההזמנות טרם נוסו מול Supabase חי כאן. בדיקות ממשק עם שירות מדומה עברו.

ניהול תפקידים:
הריצו role-management.sql אחרי admin-invitations.sql. רק אדמין משנה תפקיד מערכת. שינוי תפקיד נעצר אם נותרו שיוכים לא תואמים; אין הסרה אוטומטית של מידע.
מנהל בית ספר משייך מורים לכיתות בבית הספר שלו, ממנה מורה אחראי ומסיר שיוך אחר. אי אפשר להסיר את המורה האחראי לפני מינוי מחליף.
אי אפשר לשנות את תפקיד האדמין שלך או להסיר את האדמין האחרון. SQL משתמש בנעילה למניעת שינויים מקבילים בלתי בטוחים.

שפות:
בחירת ממשק עברית, אנגלית, רוסית וערבית, עם כיווניות מותאמת. שפת התמלול ו־OCR נבחרת בנפרד.
טיוטת AI מבקשת להשיב בשפת הממשק; איכות המודל בכל שפה לא נבדקה מול הקלטות או משימות אמיתיות כאן. תוכן המורים אינו מתורגם אוטומטית.
תרגומי מסכים עיקריים קיימים; חלק מהודעות השגיאה והסטטוסים הטכניים עדיין בעברית.

הרשמה והרשאות מפורטות:
הריצו registration-permissions.sql אחרי role-management.sql. הוא מוסיף הזמנת תלמיד לכיתה ואת school_class_permissions.
ב־Supabase Auth הגדירו אימות אימייל והוסיפו את כתובת האתר ואת /reset-password לכתובות החזרה המותרות.
מסך הרשמה דורש שם מלא, אימייל, סיסמה באורך 8 תווים לפחות ואישור סיסמה. אפשר להזין קוד או קישור הזמנה.
תפקיד אינו נבחר על ידי הנרשם. חשבון חדש הוא תלמיד; הזמנה שנשלחה על ידי מנהל מורשה קובעת תפקיד ושיוך, רק אחרי אימות אותו אימייל. ללא הזמנה החשבון ממתין לשיוך.
איפוס סיסמה משתמש בשירות Supabase Auth. הסיסמאות אינן נשמרות ב־localStorage או בטבלאות האפליקציה.
מנהל יכול לאפשר או למנוע ממורה בכיתה עדכון שיעורים, מענה לשאלות ופרסום תשובות לכל הכיתה. ההרשאות נאכפות ב־RLS ובפעולת הפרסום האטומית; לא רק בכפתורים.
ההרשאות הקיימות של מורים נשמרות כברירת מחדל אם אין שורת חריגה. השתייכות לכיתה עדיין נדרשת.
הרשמה, איפוס סיסמה ואכיפת SQL טרם נבדקו בפרויקט חי כאן; בדיקות זרימת הממשק ושמירת הנתונים עם Supabase מדומה עברו.

ניהול התראות, חשבונות וסטטיסטיקות:
הריצו management-analytics.sql אחרי registration-permissions.sql. הוא נדרש לגרסה החדשה של החיבור.
מנהלי בתי ספר רואים ספריית חשבונות ונתוני שימוש לבית הספר שלהם בלבד; רק אדמין יכול לבחור את כל המערכת או להשבית חשבון בכלל המערכת.
השבתה מונעת גישה לנתוני האפליקציה גם עם token קיים, באמצעות מדיניות restrictive ובדיקות בפונקציות שרת. היא אינה מוחקת חשבון ואינה חוסמת את כניסת Supabase Auth עצמה; הממשק מסרב לטעון נתונים לחשבון מושבת.
הנתונים כוללים כניסות, משתמשים פעילים, חשבונות לפי תפקיד וסוגי הפעולות; טווחי זמן 7/30/90 ימים וייצוא סיכום CSV.
כניסות נמדדות בעדכון auth.users.last_sign_in_at; שמירת שיעור, סימון הכנה, שאלה ותשובה נמדדים בטריגרים במסד. כניסה אחת המשויכת לכמה בתי ספר אינה נספרת פעמיים בסיכום המערכת.
הרשמות נספרות לפי מועד יצירת החשבון ב־Auth של החשבונות המשויכים להיקף הנבחר. יתר אירועי השימוש מתחילים מהפעלת טריגרי המדידה; אין שחזור של היסטוריית פעולות שלא נמדדה.
שימוש ב־OCR, תמלול ו־AI מדווח על ידי הממשק לאחר תוצאה מוצלחת ונבדל מנתוני שרת. אין העברה של תוכן שאלות, הקלטות, תמונות או טקסט טיוטות לתשתית המדידה.
בניהול התראות ניתן להפעיל/לבטל תזכורות סיום שיעור ועדכונים להורים/תלמידים לבית הספר. עדיין אין Push כשהאתר סגור.
SQL, הטריגרים על Auth והרשאות שרת עדיין לא נבדקו מול פרויקט Supabase חי כאן. בדיקות חישוב הסיכומים, הסינון ומניעת ספירה כפולה עברו.

בקשות תפקיד בהרשמה:
הריצו role-requests.sql פעם אחת אחרי all-in-one.sql (או אחרי management-analytics.sql). בהרשמה אפשר לבקש תפקיד הורה, מורה או מנהל; החשבון נוצר כתלמיד והבקשה ממתינה. רק אדמין מאשר או דוחה במסך ניהול תפקידים (פונקציית decide_school_role_request). בקשה לתפקיד אדמין אינה אפשרית. קבלת הזמנה שמעניקה את התפקיד סוגרת את הבקשה המתאימה. נבדק על Postgres 16 מקומי עם Auth מדומה.
